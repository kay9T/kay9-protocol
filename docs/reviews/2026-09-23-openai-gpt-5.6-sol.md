KAY9 Launch-Path Model Review

Reviewed commit: db65339b9dadfa7c762e9a76190a1f5fa1894b92

I read the requested launch-path contracts at that exact commit and, only where necessary to understand their behavior, the Uniswap Liquidity Launcher / CCA code they invoke.

Findings
M-01 — Mainnet deployment can substitute a non-canonical lookalike for the InitializerHook

Severity: Medium

Files: script/Deploy.s.sol:241-245; src/KAY9Genesis.sol:404-420

Deploy.s.sol defaults to the address-book InitializerHook but permits an unrestricted environment override:

solidity
cfg.initializerHook = vm.envOr("INITIALIZER_HOOK", book.initializerHook);

The Genesis constructor then tries to establish that this is the canonical InitializerHook by checking code presence, ERC-165 support, authorized(), the hook permission bits, and v4 address validity.

Those checks establish the interface and address shape. They do not establish that the contract is Uniswap's InitializerHook or that its beforeInitialize implementation actually enforces the value returned by authorized().

A crafted contract can therefore:

be CREATE2-mined to an address carrying exactly BEFORE_INITIALIZE_FLAG;

report support for IInitializerHook;

return the expected LBPStrategy from authorized();

nevertheless allow arbitrary callers through beforeInitialize.

The deployment passes KAY9Genesis._validatePoolHook().

After KAY9 launches but before its migration, an attacker can then initialize the advertised official pool key. KAY9's LBP migration subsequently fails because the pool already exists and the launch has to use the recovery pool instead.

I did not find a path from this alone to steal the raise—the recovery design protects it—but the deployed launch would no longer have the claimed canonical/unsquattable InitializerHook. The mistake is immutable.

Suggested fix

On Robinhood mainnet, do not permit INITIALIZER_HOOK to override the address book:

solidity
cfg.initializerHook = book.initializerHook;

Keep the override only for testnet/rehearsal chains. For additional defense, verify the expected deployed runtime/code hash or another canonical identity commitment rather than treating ERC-165 plus self-reported authorized() as proof of implementation identity.

M-02 — Tiny valid raises collapse the migration-success discriminator and can send a successful launch through recover()

Severity: Medium

File: src/KAY9Genesis.sol:674-689, 846-899

The launch accepts every nonzero graduation threshold:

solidity
if (p.requiredCurrencyRaised == 0) revert InvalidRequiredRaise();

Migration success is later distinguished from migration failure by testing whether Genesis holds at least half of the auction's gross raise:

solidity
return raised != 0 && address(this).balance >= raised / 2;

Integer division makes this predicate degenerate for raised == 1:

raised / 2 == 0
balance >= 0 == true

So a successfully migrated auction whose credited raise is one wei is necessarily read as though its raise came back.

A concrete sequence is:

The owner supplies otherwise-valid pricing/timing with requiredCurrencyRaised = 1.

The auction credits one wei and graduates.

LBPStrategy.migrate() succeeds and initializes the official hooked pool.

The official pool therefore exists.

_raiseCameBack() nevertheless returns true because 1 / 2 == 0.

_migrationOutcome() reports failure instead of success.

settle() refuses to execute.

If Genesis has zero ETH, recover() also initially refuses because ethAmount == 0.

Any account can then send one wei to Genesis and invoke recover().

The launch creates a second, hookless recovery pool even though the official migration actually succeeded, and poolKey() subsequently resolves to that recovery pool.

Without the one-wei donation, settlement/team unlocking can remain blocked; with it, the launch permanently ends with two liquidity pools and a false recorded migration outcome.

The production Launch.s.sol is unlikely to generate such an economically tiny launch, but the on-chain owner interface explicitly accepts it. The advertised invariants therefore do not hold over the contract's accepted parameter space.

The same class of ambiguity exists for other very small raises if successful migration dust approaches the truncated half-raise threshold.

Suggested fix

At minimum, use ceiling division:

solidity
uint256 halfRaised = raised / 2 + raised % 2;

and reject economically meaningless graduation thresholds.

More robustly, establish and enforce a minimum raise comfortably above the proven maximum successful-migration currency dust, then compare returned ETH against that bound. The current half-raise heuristic explicitly depends on “success dust ≪ raise” but the contract never enforces the premise.

L-01 — Successful migration may permanently leave raised-ETH dust in Genesis

Severity: Low

File: src/KAY9Genesis.sol:423-425, 599-607, 872-899

The code itself acknowledges at 874-875 that a successful LBP migration can return currency dust to Genesis:

“A successful migration leaves this contract with currency dust…”

That follows the canonical LBP behavior: after position creation, unused currency is forwarded to migrationParams.recipient, which KAY9 fixes to Genesis.

Once migration is classified as successful, settle():

records success;

sweeps unsold KAY9;

calls _settleRemainder(), which handles KAY9 only.

It does not consume address(this).balance.

recover() is the only Genesis function that subsequently spends native ETH, but it rejects a successfully migrated launch.

Consequently, any successful-migration currency dust is permanently trapped in Genesis rather than ending in the locked liquidity position.

This does not provide an extraction path and the expected amount is dust, but it contradicts property 4 as written: not literally every wei raised is guaranteed to end in locked liquidity.

Suggested fix

Either:

consume any success-path ETH residual during settle() together with the remaining KAY9 into locked liquidity; or

formally derive and enforce a maximum residual, expose it explicitly as accepted unrecoverable dust, and change the claimed invariant from “every ETH raised” accordingly.

A withdrawal is not an appropriate fix because that would weaken the stronger no-withdraw property.
